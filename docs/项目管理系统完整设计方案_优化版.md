## 〇、本次评审的核心优化点（先说结论）

| # | 原方案问题 | 优化建议 | 原因 |
|---|---|---|---|
| 1 | `invoice_sales` 和 `invoice_purchase` 两张表结构几乎完全一致 | 合并为一张 `invoice` 表，用 `direction`（1-销项/2-进项）字段区分，与 `payment_record` 的设计保持一致 | 减少表冗余，未来加字段只改一处，统计 SQL 也能一张表搞定，不用 UNION |
| 2 | 所有表用 `DELETE` 物理删除，但又有 `operation_log` 记录 DELETE 操作 | 核心业务表（合同/付款/发票/项目）改为**软删除**（`is_deleted` + `deleted_at`），日志里能追溯到被删的历史数据 | 硬删除后 operation_log 里的 `business_id` 会变成"查无此数据"的悬空引用，审计追溯形同虚设 |
| 3 | 无并发控制字段 | 核心表加 `version` 字段做乐观锁 | 财务/合同类数据多人协作时容易出现覆盖写入 |
| 4 | 合同表没有标注"我方是甲方还是乙方" | `contract` 增加 `our_party_role` 字段（1-我方为甲方，2-我方为乙方） | 否则每次统计"应收/应付"都要先判断 `party_a_id`/`party_b_id` 里哪个的 `company_type=1`，业务代码里到处写这个判断很容易出错 |
| 5 | 发票"红冲"没有关联原发票 | `invoice` 增加 `original_invoice_id` 字段 | 红冲票必须能追溯冲的是哪一张，否则财务对账对不上 |
| 6 | 枚举值（公司类型/状态/角色）全部硬编码在字段注释里 | 增加 `sys_dict`（数据字典）表，前端下拉选项走接口而不是写死 | 原设计"扩展性"原则里提到要支持自定义字段，硬编码枚举与这条原则矛盾 |
| 7 | 权限模型只到"角色"粒度，没有"数据行级权限" | 明确"仅本人负责的项目/合同"这类权限的判断逻辑（`manager_id`/`created_by` = 当前用户），并在 API 层做行级过滤 | 角色矩阵里写了"创建/编辑自己负责的"，但没有落地到具体判断字段 |
| 8 | UI/UE 设计只给了首页和合同详情两个 ASCII 线框图 | 本文档第五章给出**全部核心页面**的线框、交互状态、视觉规范 | 你的原始要求 |
| 9 | 付款金额与合同金额的一致性校验只在思路里提了一句 | 在业务规则里明确写出校验触发时机（新增付款时后端强校验） | 避免超收/超付却没有拦截 |
| 10 | 部署方案没有备份、监控、日志轮转 | 第七章补充最小可行的运维方案 | 生产可用性 |

以下正文按照「系统概述 → 功能描述 → 数据模型增量 → 信息架构 → UI/UX 详细设计 → 状态流程 → 非功能性设计 → 排期」组织。

## 一、系统概述

### 1.1 系统定位
面向中小型企业的轻量级项目合同管理系统，实现**项目全生命周期管理、合同全流程跟踪、财务收支一体化管理**。

### 1.2 核心业务模块（保留原设计，新增"系统管理"）

| 模块 | 功能描述 |
|---|---|
| 公司管理 | 管理合作方公司信息（客户、供应商、合作伙伴） |
| 用户管理 | 系统用户账号、角色权限管理 |
| 项目管理 | 项目立项、进度跟踪、状态管理 |
| 合同管理 | 合同录入、甲乙方关联、状态管理 |
| 付款管理 | 多笔付款/收款记录，支持支付凭证上传 |
| 发票管理 | 销项/进项发票录入、附件上传、与付款核销 |
| 统计报表 | 合同金额汇总、付款统计、发票统计 |
| **系统管理（新增）** | 数据字典维护、操作日志查询、系统参数配置 |

### 1.3 设计原则
- **数据一致性**：统一公司主数据，避免信息孤岛
- **操作可追溯**：关键操作记录创建人、创建时间；核心数据软删除，历史可查
- **扩展性**：字典化枚举值，预留自定义字段接口，支持未来二次开发
- **安全性**：基于公司 ID 进行数据隔离，用户只可见本公司数据；行级权限控制"仅本人负责"的数据
- **并发安全**：核心业务表使用乐观锁，避免多人协作时的覆盖写入

> 技术架构、技术栈选型（Vue3 + Element Plus + Spring Boot 3 + MyBatis-Plus + MySQL + Redis + MinIO）与原方案一致，此处不再重复，仅在第三章列出数据结构的增量变更。

## 二、功能架构与详细功能描述

> 原方案的模块表只写了一句话概述，这一章把每个模块拆到"功能点 + 业务规则"的颗粒度，方便直接转成开发任务卡。

### 2.1 公司管理
**功能点：**
1. 新增/编辑/查看/停用公司档案（不做物理删除，只能停用）
2. 公司类型多选筛选（本公司/客户/供应商/合作伙伴），列表左侧提供类型 Tab 快速切换
3. 统一社会信用代码查重校验（新增时若已存在提示"是否为同一家公司"）
4. 公司详情页可直接跳转查看：该公司作为甲方/乙方参与的合同列表
5. 支持 Excel 批量导入公司名录（EasyExcel），导入前预校验并展示错误行

**业务规则：**
- `company_type = 1`（本公司）的记录只允许系统初始化时创建 1～N 条（对应集团多主体场景），不允许普通用户新增
- 公司被合同引用后，`company_name` 允许改，但不允许直接停用（需先确认无生效中合同）

### 2.2 用户与权限管理
**功能点：**
1. 用户 CRUD、重置密码（管理员操作，重置后强制下次登录修改）
2. 角色分配（超级管理员/管理员/财务/普通成员），可扩展为多角色叠加（预留 `user_role` 关联表）
3. 个人中心：修改自己的密码、头像、联系方式
4. 登录日志查看（最近 10 次登录时间、IP、设备）

**业务规则（角色权限矩阵，保留原设计并补充行级权限说明）：**

| 功能模块 | 超级管理员 | 管理员 | 财务 | 普通成员 |
|---|---|---|---|---|
| 公司管理 | 全部操作 | 查看 | 查看 | 查看 |
| 用户管理 | 全部操作 | 本公司用户管理 | 查看 | 查看 |
| 项目管理 | 全部操作 | 全部操作 | 查看 | 仅 `manager_id = 当前用户` 的项目可创建/编辑 |
| 合同管理 | 全部操作 | 全部操作 | 查看 | 仅 `created_by = 当前用户` 的合同可创建/编辑 |
| 付款记录 | 全部操作 | 查看 | 全部操作 | 查看 |
| 发票管理 | 全部操作 | 查看 | 全部操作 | 查看 |
| 统计报表 | 全部 | 全部 | 查看财务报表 | 查看基础报表 |

> 落地方式：后端在 Service 层对"普通成员"角色的查询/更新接口追加 `AND (manager_id = #{currentUserId} OR created_by = #{currentUserId})` 的过滤条件，而不是仅在前端隐藏按钮。

### 2.3 项目管理
**功能点：**
1. 项目立项（编号自动生成规则：`XM-年份-三位序号`，如 `XM-2026-008`）
2. 项目状态看板：立项 / 进行中 / 验收 / 结项 / 暂停，支持看板视图和列表视图切换
3. 项目详情页聚合展示：基本信息、关联合同列表（含金额汇总）、进度时间轴
4. 项目延期预警：`end_date` 已过但状态仍为"进行中"时，列表中标红并在首页提醒

**业务规则：**
- 项目状态变更需要记录操作日志，"结项"前需校验关联合同是否均已"终止"或"生效"状态（不能有"草稿"合同挂在已结项项目下）

### 2.4 合同管理
**功能点：**
1. 合同录入：选择所属项目 → 自动带出项目所属公司为默认一方 → 选择另一方公司 → 系统自动判断/手动确认 `our_party_role`
2. 合同编号规则：`HT-年份-三位序号`
3. 合同列表多维度筛选：项目、甲方、乙方、状态、签订日期区间、是否即将到期
4. 合同详情页四个 Tab：付款记录 / 销项发票 / 进项发票 / 附件，每个 Tab 内可直接新增
5. 合同金额变更：当合同处于"变更中"状态时，允许修改 `total_amount`，系统自动生成一条变更记录（新增 `contract_change_log` 表，见第三章）
6. 合同到期预警：到期前 30/15/7 天分级提醒，首页 + 消息通知双通道

**业务规则：**
- 新增付款/发票时，后端强校验：`该合同累计付款/收款金额 + 本次金额 ≤ 合同总金额`（超出则拦截并提示"超出合同金额 X 元，请确认"，超级管理员可强制通过并记录日志）
- 合同状态为"终止"后，禁止新增付款/发票记录，仅可查看

### 2.5 付款 / 收款管理
**功能点：**
1. 新增付款/收款记录，方向自动根据合同的 `our_party_role` 推导默认值（我方为乙方→默认"收款"，我方为甲方→默认"付款"），可手动改
2. 支付凭证上传（图片/PDF），支持拖拽多文件上传，上传后自动 OCR 识别金额辅助校验（可选，二期功能）
3. 待确认状态的记录支持"确认到账"操作（financial 角色专属按钮）
4. 按合同/按方向/按日期区间/按状态多条件筛选，列表可导出 Excel

**业务规则：**
- 记录一旦被发票核销（存在关联的 `invoice.payment_record_id`），不允许删除，只能作废（新增 `status=2 已作废`）

### 2.6 发票管理
**功能点：**
1. 销项/进项发票在同一个页面用 Tab 切换（复用同一套表单组件，因为字段完全一致）
2. 新增发票时：输入不含税金额 + 税率 → 前端自动计算税额、价税合计（实时联动，不需要手动算）
3. 发票核销：新增发票时可选择关联某笔付款/收款记录，系统自动校验"该笔付款/收款已核销金额 + 本次发票金额 ≤ 付款/收款金额"
4. 支持"预开票"（不关联付款记录），后续可以在发票详情页手动补充核销关系
5. 红冲操作：选中一张已开票记录 → 点击"红冲" → 系统自动生成一张 `amount` 为负数、`original_invoice_id` 指向原票的红冲记录，原票状态改为"已红冲"
6. 进项发票额外支持"认证抵扣"状态流转

**业务规则：**
- 发票号码全局唯一（不区分销项/进项，合并表后天然满足）
- 红冲后不可再次红冲同一张票

### 2.7 附件管理
**功能点：**
1. 统一附件池，按 `business_type + business_id` 关联到具体业务记录
2. 支持的文件类型白名单校验（图片、PDF、Office 文档），单文件不超过 20MB
3. 附件预览：图片直接预览，PDF 用内嵌 viewer 打开，其他类型仅支持下载

### 2.8 统计报表
**功能点：**
1. 首页概览卡片：合同总数/总金额、已收款、未收款，同比/环比增长率
2. 合同签约趋势折线图（近 12 个月）
3. 收付款汇总报表：可按月/季/年聚合
4. 客户合同排行榜（Top 10）
5. 全部报表支持导出 Excel / 导出 PDF

### 2.9 系统管理（新增模块）
**功能点：**
1. 数据字典维护：公司类型、合同状态、发票类型等枚举统一在字典表管理，前端下拉框调接口获取，而不是写死在代码里
2. 操作日志查询：按用户/模块/时间筛选，支持查看变更前后的 JSON diff
3. 系统参数配置：如"合同到期提醒天数""文件上传大小限制"等可配置项

## 五、UI / UX 详细设计方案

### 5.1 视觉设计规范

| 类别 | 规范 |
|---|---|
| 主色 | `#2563EB`（蓝，用于主按钮、Tab 激活态、图表主色） |
| 辅助色 | 成功 `#16A34A`；警告 `#F59E0B`；危险 `#DC2626`；中性文字 `#374151` |
| 背景 | 页面背景 `#F5F7FA`，卡片背景 `#FFFFFF` |
| 字体 | 系统默认字体栈，正文 14px，标题 16-20px，数据强调数字 24-28px（首页卡片） |
| 圆角 | 卡片 8px，按钮/输入框 4px |
| 间距 | 8px 基准网格（8/16/24/32） |
| 组件库 | Element Plus 默认组件，通过 CSS 变量覆盖主题色，不做深度定制以控制开发成本 |

### 5.2 全局交互规范
- **加载态**：列表/表格统一使用骨架屏（skeleton），按钮提交中禁用并显示 loading 图标，避免重复提交
- **空状态**：列表无数据时显示插画 + 引导文案（如"暂无合同，点击右上角新增"），不要只显示空白表格
- **表单校验**：失焦校验 + 提交前统一校验，错误信息显示在字段下方（红色小字），金额类字段禁止负数（红冲场景走专门的红冲按钮而非手动录入负数）
- **危险操作二次确认**：删除、停用、红冲、强制超额通过等操作统一弹出 `ElMessageBox.confirm`，文案说明后果（如"红冲后原发票将不可编辑，是否继续？"）
- **消息反馈**：成功用绿色 Toast（3 秒自动消失），失败用红色 Toast（不自动消失，需手动关闭），避免用 alert
- **分页**：所有列表统一使用 Element Plus 的 `el-pagination`，默认每页 20 条，支持 10/20/50/100 切换

## 六、核心状态流转

### 6.1 合同状态流转
```
草稿 → 生效 → 变更中 → 生效（变更完成回到生效态，写变更履历）
              ↓
             终止（生效状态下可随时终止，终止后不可逆）
```

### 6.2 发票核销与红冲流程
```
新增发票 → 是否关联付款记录？
  是 → 校验核销额度 → 通过则保存（状态=已开票）→ 后续可"认证抵扣"（仅进项）
  否 → 保存为"预开票" → 后续可在发票详情页手动补充核销关系
已开票发票 → 点击"红冲" → 生成金额为负的红冲记录（original_invoice_id 指向原票）
          → 原票状态改为"已红冲"，不可再操作
```

## 七、非功能性优化建议

| 类别 | 原方案 | 优化建议 |
|---|---|---|
| 备份 | 未提及 | MySQL 每日全量 + binlog 增量备份，保留 30 天；MinIO 开启版本控制 |
| 监控 | 未提及 | 最小化方案：Spring Boot Actuator + Prometheus + Grafana 看服务健康度；日志用 ELK 或轻量的 Loki |
| 日志轮转 | 未提及 | Logback 按天切割 + 保留 30 天，超期自动清理，避免磁盘打满 |
| HTTPS | Nginx 443 端口预留但无证书说明 | 生产环境用 Let's Encrypt 自动续期证书 |
| 文件上传安全 | 未提及 | 后端二次校验文件类型（不仅信前端 MIME），限制单文件大小，存储路径不使用用户可控字符串拼接，防止路径穿越 |
| 接口限流 | 未提及 | 登录接口、导出接口加限流（如 Sentinel 或简单的 Redis 计数器），防止暴力破解和批量爬取 |
